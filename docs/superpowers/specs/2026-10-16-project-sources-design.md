# Подключение проектов к rag-mcp — дизайн

Дата: 2026-10-16 · Статус: на ревью

## Зачем

Сейчас документы попадают в индекс одним путём: их копируют в `data/docs/<проект>/`.
Копии устаревают, симлинк на папку не работает (`iter_files` не заходит в папки-симлинки),
а проект определяется только по совпадению имени папки. Нужно, чтобы пользователь в папке
своего проекта набрал `rag-mcp add` (или попросил агента) и дальше поиск из Claude Code в этом
проекте — в том числе из worktree и второго клона — отвечал по его документам.

**Успех:** в репозитории `~/work/shop` выполнено `rag-mcp add`; поиск из Claude Code, открытого
в `~/work/shop`, в worktree `~/orca/worktrees/ATS-3010` того же репо или в клоне
`~/tmp/shop-copy` с тем же origin, возвращает документы `shop` со скоупом `project` и без
копирования файлов. Установка с нуля доводит пользователя до этого состояния одной командой.

## Решения (согласованы)

| Вопрос | Решение |
|---|---|
| Что индексировать при `add` | весь репозиторий по git: отслеживаемые и новые неигнорируемые файлы; без git — обход с исключениями |
| Как определять проект вне подключённой папки | путь → git origin → общий `.git` → имя папки (старое правило) |
| MCP | `add_project` с фоновой индексацией + подсказка в `search`; `remove_project` в MCP нет |
| Установщик | проверка Ollama; установка Ollama с согласия; конфиги Claude Desktop и Cursor; `--add <путь>` |
| Подход | A — виртуальный префикс: подключённый проект виден индексу как `source = <имя>/<путь>` |

Отвергнуто: симлинк в `data/docs` (симлинки на Windows требуют прав, git-фильтр сбоку, метаданные
всё равно нужны); отдельный индекс на проект (переписывание хранилища и слияние индексов ради
поиска по всем проектам и `common/`).

## Не делаем

- Индексы на ветку: worktree на другой ветке ищет по документам подключённой копии (см. ч. 2).
- Удаление проектов агентом (`remove_project` в MCP).
- Фильтры `--include/--exclude`: подключение подпапки (`rag-mcp add ./docs`) закрывает этот случай.
- Английский README.

## Часть 1. Реестр и индексация

### Реестр

Файл `<index_dir>/projects.json` (по умолчанию `data/index/projects.json`): машинно-локальное
состояние с абсолютными путями, лежит рядом с индексом. `ingest --rebuild` (`store.reset()`)
его не трогает.

```json
{
  "shop": {
    "path": "/Users/a/work/shop",
    "origin": "github.com/acme/shop",
    "git_dir": "/Users/a/work/shop/.git",
    "added": "2026-10-16"
  }
}
```

- `origin` — нормализованный `remote.origin.url`: без схемы, пользователя, порта и `.git`,
  `host:owner/repo` → `host/owner/repo`, всё в нижнем регистре (GitHub и GitLab не различают
  регистр в путях, а клоны бывают сделаны по адресу в другом регистре). Примеры:
  `git@github.com:Acme/shop.git`, `https://user@github.com/Acme/shop`, `ssh://git@github.com:22/Acme/shop.git`
  → `github.com/acme/shop`. `null`, если origin нет.
- `git_dir` — абсолютный `git rev-parse --git-common-dir` (общий для всех worktree). `null` без git.
- Запись атомарная (`_atomic_write`, как у манифеста).

### Что подключается

- `rag-mcp add` без пути → корень git-репо текущей папки (`git rev-parse --show-toplevel`);
  вне git — сама текущая папка.
- `rag-mcp add <путь>` → ровно этот путь (можно подпапку репо: `rag-mcp add ./docs`).
- Имя по умолчанию — имя основного репозитория: папка над `git_dir` (для `add` из worktree
  `ATS-3010` проект называется `shop`). Вне git — имя папки. `--name` задаёт своё.
- Допустимое имя: `[A-Za-z0-9._-]+`, не начинается с точки.

### Отказы `add`

| Условие | Сообщение (суть) |
|---|---|
| имя занято папкой `data/docs/<имя>/` | имя занято, задайте `--name` |
| имя занято другим проектом с другим путём | то же |
| путь внутри уже подключённого или содержит его | вложенные проекты запрещены, сначала `remove` |
| путь внутри `docs_dir` | эти файлы уже индексируются из `data/docs` |
| путь — домашняя папка или корень диска | слишком широко; CLI: `--force` |
| подходящих файлов (после фильтра по типам) > 5000 | слишком много; CLI: `--force`; в MCP отказ без исключений |
| путь не существует / не папка | — |

Повторный `add` того же пути под тем же именем идемпотентен: обновляет `origin`, `git_dir`.

### Обход файлов

- git-папка: `git -C <path> ls-files -z --cached --others --exclude-standard` (отслеживаемые +
  новые неигнорируемые). Пути из вывода относительно `<path>`.
- Без git или если `ls-files` упал (битый репо, «dubious ownership»): `rglob` с пропуском
  скрытых сегментов и каталогов `node_modules .venv venv build dist target vendor __pycache__`;
  в отчёт ingest — предупреждение.
- Всегда: только `SUPPORTED_SUFFIXES` (`.md .markdown .txt .pdf`), без скрытых сегментов
  (`_hidden`), только обычные файлы. Если `docs_dir` лежит внутри пути — его поддерево пропускается.

### Индексация

Новая функция обхода источников отдаёт пары `(path, source)`:

- файлы `docs_dir` — как сейчас, `source = path.relative_to(docs_dir)`;
- файлы подключённого проекта — `source = f"{name}/{rel}"`.

`load_document(path, source)` принимает `source` готовым. Всё ниже не меняется: `doc_id_for(source)`,
`project_of(source)` (= имя), скоуп `scope_for`, `common/`, `fetch_document`, Qdrant-фильтр по
`project`, `needs_ingest` по `stat` (T-008). `Pipeline._ingest` и `needs_ingest` идут по этой
функции вместо `iter_files(docs_dir)`.

### Отключение

`rag-mcp remove <имя>` удаляет запись из реестра и запускает ingest: документы проекта не попадают
в `seen` и удаляются из индекса.

## Часть 2. Определение проекта

**Рабочие папки** — как сейчас: MCP roots → `CLAUDE_PROJECT_DIR` → cwd сервера. CLI `search`
без `--project` теперь тоже определяет проект по cwd; `--all` — искать везде (новый флаг).

**Порядок** (первое совпадение):

0. Явный проект: параметр `project` / `--project` (`explicit`) или `RAG_PROJECT` (`env`) — без изменений.
1. **path** — рабочая папка внутри зарегистрированного `path` или равна ему. Сравнение после
   `os.path.realpath` + `os.path.normcase`. Вложенные регистрации запрещены (ч. 1), поэтому
   совпадение по пути всегда одно.
2. **origin** — `git -C <папка> remote get-url origin`, нормализация (ч. 1), сравнение с реестром.
3. **git_dir** — `git -C <папка> rev-parse --git-common-dir` (абсолютный) совпал с реестром.
   Ловит worktree репо без origin.
4. **name** — старое правило: имя папки или её родителя совпадает с проектом в `data/docs`.
5. Нет совпадения → скоуп `all` + `hint` (ч. 3).

Если на шаге 2 совпало несколько проектов (два клона одного репо подключены под разными
именами), берётся тот, чей `git_dir` совпал; иначе первый по имени, а в ответе `note` со списком.

**Кэш:** результат по `(путь, mtime_ns реестра)` хранится в процессе; git на папку запускается
один раз за сессию. Таймаут каждого вызова git — 2 с. Нет `git` в PATH → шаги 2–3 пропускаются.

**Прозрачность:** в `scope` ответа `search` и в `index_status` — `matched_by`
(`explicit | env | path | origin | git_dir | name`) и, если совпало не по `path`, `docs_from` — путь
подключённой копии.

**Принятое ограничение:** worktree на другой ветке ищет по документам подключённой копии.
Нужны документы именно этой ветки — подключить worktree отдельно под другим именем.

## Часть 3. CLI и MCP

### CLI

| Команда | Поведение |
|---|---|
| `rag-mcp add [путь] [--name N] [--force]` | регистрирует (ч. 1) и сразу индексирует в терминале; печатает имя, путь, origin, найдено/проиндексировано файлов и как проверить |
| `rag-mcp remove <имя>` | удаляет из реестра + ingest |
| `rag-mcp projects` | таблица: имя, путь, тип (`connected` / `folder` в `data/docs`), документы, чанки; «путь не найден»; «← здесь» для проекта текущей папки |
| `rag-mcp search … [--all]` | без `--project`/`--source` — проект по cwd (ч. 2) |
| `rag-mcp status` | + реестр |
| `rag-mcp register …` | ч. 4 |

`add` и `remove` берут `index.lock` (тот же `write_lock`, что у ingest); занято → `IndexBusy`
с текстом «индекс занят, повторите».

### MCP

- `add_project(path: str | None = None, name: str | None = None)`:
  путь по умолчанию — первая рабочая папка клиента. Те же проверки, что у CLI `add`, без `--force`.
  Регистрирует и запускает ingest в **фоновом потоке**; сразу отвечает
  `{"project", "path", "files", "indexing": "started"}`. Если индекс занят другим процессом —
  проект зарегистрирован, `indexing: "pending"` + `note`: проиндексируется при следующем
  `reindex` или старте сервера (`needs_ingest` увидит новые файлы).
- Одна фоновая индексация на процесс. `reindex` во время неё → «индекс занят, повторите позже».
- `index_status` дополнительно: `projects` (реестр с `exists`) и `ingest`:
  `{"running": true, "project", "started"}` либо последний отчёт (`added`, `updated`, `removed`,
  `errors`, `finished`).
- `search`: когда скоуп `all` из-за того, что рабочая папка ничему не соответствует, в ответе
  `hint`: «папка <путь> не подключена; `add_project` проиндексирует её документы».
- `INSTRUCTIONS`: если пользователь спрашивает про документы текущего проекта, а `search` вернул
  `hint`, предложить `add_project`. Подтверждение вызова спрашивает сам клиент.

## Часть 4. Установщик и README

### Глобальная команда

`uv --directory <repo> run rag-mcp …` меняет cwd на репозиторий rag-mcp, поэтому `add .` подключил
бы сам rag-mcp. Установщик ставит команду в PATH: `uv tool install --editable --force <repo>`.
`PROJECT_ROOT` по-прежнему указывает на репо (editable), `.env` и `data/` берутся оттуда.
MCP-серверы регистрируются как раньше, через `uv --directory <repo> run rag-mcp serve`.

### `install.sh` / `install.ps1`

1. `uv`, `uv sync`, `uv tool install --editable`, `.env` из примера, папки `data/`.
2. Ollama:
   - не установлена → «Установить Ollama? [y/N]»: macOS — `brew install ollama` (без brew —
     ссылка на ollama.com/download), Linux — официальный `install.sh`, Windows —
     `winget install Ollama.Ollama`;
   - установлена, не отвечает на `OLLAMA_URL` → запуск (macOS: `open -a Ollama`, иначе
     `ollama serve` в фоне), ожидание до 10 с;
   - нет модели `RAG_EMBED_MODEL` → `ollama pull`.
3. Клиенты: `rag-mcp register` (ниже).
4. `--add <путь>` → `rag-mcp add <путь>`; без флага — подсказка `cd ваш-проект && rag-mcp add`.
5. Итог: список ✓/✗ (uv, команда rag-mcp, Ollama запущена, модель, клиенты, проект и число
   документов) и следующий шаг.

Флаги: `--yes` (все вопросы — да), `--no-ollama`, `--no-claude`, `--add <путь>`; в PowerShell
`-Yes -NoOllama -NoClaude -Add`. Без TTY (CI) каждый вопрос — «нет».

### `rag-mcp register [--claude-code] [--claude-desktop] [--cursor] [--yes]`

Python, одна реализация для всех ОС. Без флагов — все найденные клиенты.

- Claude Code: `claude mcp remove -s user rag-mcp` + `claude mcp add -s user rag-mcp -- <uv> --directory <repo> run rag-mcp serve`, если `claude` в PATH.
- Claude Desktop: `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS),
  `%APPDATA%\Claude\claude_desktop_config.json` (Windows); только если каталог существует.
- Cursor: `~/.cursor/mcp.json`; только если `~/.cursor` существует.
- Для файловых конфигов: вопрос (или `--yes`), бэкап `<файл>.bak-<YYYYMMDD-HHMMSS>`, слияние
  JSON — добавляется/заменяется только `mcpServers["rag-mcp"]`, остальное сохраняется.
  `command` — абсолютный путь к `uv` (`shutil.which`), потому что GUI-приложения не видят PATH
  терминала. Невалидный JSON — отказ без записи.

### README (русский)

1. Что это и зачем — 3 строки и пример вопроса агенту.
2. Быстрый старт: установка → `rag-mcp add` в своём проекте → вопрос в Claude.
3. Подключение проектов: что индексируется, определение проекта и `matched_by`, worktree и
   клоны, старая раскладка `data/docs` и `common/`.
4. Таблицы команд CLI и MCP-инструментов; пример ответа `search` (`scope`, `matched_by`,
   `docs_from`, `degraded`, `hint`).
5. Все `RAG_*` с умолчаниями, включая JSON-формат `RAG_SHARED_PROJECTS`.
6. Клиенты: Claude Code, Desktop, Cursor — `rag-mcp register`, пути конфигов, ручной JSON.
7. Неполадки: Ollama не запущена / нет модели (`degraded`), пустой индекс, проект не
   определился, сервера нет в `/mcp`, `uv` не в PATH GUI-приложений, индекс занят.
8. Обновление (`git pull` + установщик) и удаление (`uv tool uninstall rag-mcp`,
   `claude mcp remove -s user rag-mcp`, удалить `data/`).
9. Разработка.

## Часть 5. Ошибки и тесты

### Ошибки

- **Путь проекта пропал:** ingest не удаляет его чанки (doc_id проекта считаются `seen`) и пишет
  в отчёт: «проект X: путь не найден — `rag-mcp remove X` или `add` с нового места».
  `needs_ingest` такие проекты не учитывает. `projects` и `index_status` показывают `exists: false`.
- **git:** нет `git` или папка не репо → обход с исключениями, шаги 2–3 определения пропускаются;
  `ls-files` упал → обход с исключениями + предупреждение в отчёте.
- **Реестр:** `add`/`remove` под `index.lock`; повреждённый `projects.json` → ошибка с путём к
  файлу, без перезаписи. `add`, `add_project`, `remove` и **ingest отказывают** (иначе ingest
  принял бы реестр за пустой и удалил чанки всех подключённых проектов); поиск по уже
  проиндексированному работает, определение проекта откатывается к правилу `name`.
- **Ollama упала во время индексации:** ошибки файлов в отчёте, файлы не в манифесте,
  `needs_ingest` повторит на следующем `reindex`/старте; `index_status` покажет отчёт.
- **Конфиги клиентов:** невалидный JSON — отказ без записи; всегда бэкап перед записью.

### Тесты (pytest; временные git-репо создаются в тестах)

- Реестр: add/remove/повторный add; правила имени; конфликт с `data/docs`; вложенность; дом/корень;
  лимит файлов и `--force`; повреждённый `projects.json` (ingest отказывает, чанки целы);
  нормализация origin (таблица примеров).
- Обход: неотслеживаемые неигнорируемые — да, `.gitignore` и скрытые — нет; без git пропускается
  `node_modules`; `docs_dir` внутри пути пропускается.
- Индексация: документы проекта ищутся под `<имя>/…` и скоупятся; `remove` убирает чанки;
  пропавший путь сохраняет чанки, `needs_ingest() is False`.
- Определение: path; worktree (`git worktree add`) через git_dir; второй клон с тем же origin;
  name; нет совпадения → `hint`; кэш сбрасывается при изменении реестра; `matched_by`, `docs_from`.
- CLI: `add` из подпапки репо находит корень; `search` по cwd; `--all`.
- MCP: `add_project` регистрирует, фоновая индексация завершается (тест ждёт поток); `index_status`
  показывает реестр и `ingest`; `reindex` во время фоновой индексации — «занят».
- `register`: слияние JSON во временном HOME, бэкап, идемпотентность, чужие серверы сохраняются,
  невалидный JSON не перезаписывается.
- CI: установщики с `--no-ollama --no-claude --add examples/docs`, затем `rag-mcp search` и
  `rag-mcp projects`. Установка и запуск Ollama, запись в реальные конфиги — ручной чек-лист в PR.
